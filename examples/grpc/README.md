# netx/grpcx — gRPC example

A `people.v1.PeopleService` that moves a `Person` entity and its photo
through every gRPC call shape, with two servers to choose from and one client
that works with both:

| Command | What it runs |
|---------|--------------|
| `grpc-server` | gRPC only, on `:9090` |
| `http-grpc-server` | **one** gofi service with gRPC on `:9090` and HTTP on `:8080` over the same store |
| `client` | calls every RPC, uploads and downloads a photo, chats |

```
grpc/
├── .env                      # APP_ENVIRONMENT=dev (read automatically outside prod/stage)
├── proto/people/v1/people.proto
├── gen/people/v1/            # generated by `go generate .` (committed)
├── generate.go               # the protoc command
├── people/                   # domain: Person, PhotoInfo, in-memory Store, AppErrors
├── grpcapi/                  # PeopleService implementation + bearer auth
├── httpapi/                  # GET /people, /people/{id}, /people/{id}/photo
├── grpc-server/main.go       # gofi.New().With(grpcserver.New(...))
├── http-grpc-server/main.go  # gofi.New().With(grpcserver.New(...), httpserver.New(...))
└── client/main.go
```

## The RPCs

| RPC | Shape | What travels |
|-----|-------|--------------|
| `CreatePerson`, `GetPerson` | unary | a `Person` (nested `Address`, repeated phones, timestamps) |
| `ListPeople` | server streaming | one `Person` per message until the server ends the stream |
| `UploadPhoto` | client streaming | the person ID, then the image in 16 KiB chunks; one `PhotoInfo` back |
| `DownloadPhoto` | server streaming | `PhotoInfo` first, then the image in 32 KiB chunks |
| `Chat` | bidirectional | both sides send whenever they want; the client sends and receives concurrently |

Both sides check the image's SHA-256, and the server detects the image type
from the bytes and does not trust what the client says. Anything other than PNG, JPEG, GIF or WebP, or
anything over 5 MiB, is rejected with `InvalidArgument`.

## Run

Its own Go module: no database or broker needed.

```sh
cd examples/grpc

# terminal 1: pick one server
go run ./http-grpc-server     # gRPC :9090 + HTTP :8080
go run ./grpc-server          # gRPC :9090 only

# terminal 2
go run ./client                          # generates a PNG
go run ./client -image ~/photo.jpg       # or upload your own
```

The client prints each step:

```
== 4. client streaming: UploadPhoto in chunks
sent 6 chunks
uploaded 94772 bytes, server says image/png, 94772 bytes, sha256 5362adf89ee4…

== 5. server streaming: DownloadPhoto in chunks
received 3 chunks, 94772 bytes, checksum ok, saved to downloaded-photo.png

== 6. bidirectional streaming: Chat
  → hello
  ← server: connected, say something
  ← server: hi Ada Lovelace, you said "hello"
```

With `http-grpc-server`, what was written over gRPC is readable over HTTP:

```sh
curl localhost:8080/people
curl localhost:8080/people/p-1
curl localhost:8080/people/p-404          # 404 with errorCode PERSON_NOT_FOUND
open http://localhost:8080/people/p-1/photo   # the photo uploaded through gRPC
curl localhost:8080/readyz
```

### grpcurl

Reflection is on, and listed as a public method so it needs no token:

```sh
grpcurl -plaintext localhost:9090 list
grpcurl -plaintext localhost:9090 describe people.v1.PeopleService
grpcurl -plaintext -H 'authorization: Bearer secret-token' \
  -d '{"name":"Linus","email":"linus@example.com"}' \
  localhost:9090 people.v1.PeopleService/CreatePerson
grpcurl -plaintext -H 'authorization: Bearer secret-token' localhost:9090 people.v1.PeopleService/ListPeople
grpcurl -plaintext localhost:9090 grpc.health.v1.Health/Check     # always public
```

Calls without `authorization: Bearer secret-token` get `Unauthenticated`.

## Errors across the wire

Handlers return the domain's `errs.AppError` unchanged. `grpcx` maps the kind
to a status code and sends the AppError code in an `ErrorInfo` detail, never
the cause. On the client, `grpcx.FromError` turns it back into an AppError:

```
error kind=VALIDATION code=INVALID_PERSON message="invalid person: email \"not-an-email\" is not valid"
error kind=NOT_FOUND code=PERSON_NOT_FOUND message="person p-404 not found"
```

The HTTP server maps the same AppError with `httpx.RespondError`, so one
domain error yields `NotFound` over gRPC and `404` over HTTP.

## Changing the contract

Edit `proto/people/v1/people.proto` and regenerate (needs `protoc`,
`protoc-gen-go` and `protoc-gen-go-grpc` on `PATH`):

```sh
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.5.1
go generate .
```

## API used

| Area | API |
|------|-----|
| Service | `gofi.New`, `With`, `Build`, `ListenAndServe` |
| gRPC server | `grpcserver.New` with `grpcx.ServerConfig` (`Auth`, `Reflection`), `Register` |
| HTTP server | `httpserver.New` with `httpx.WSConfig` (`Health`), `Handlers` |
| gRPC client | `grpcx.NewClient` with `grpcx.ClientConfig` (`Insecure`, `Token`, `Timeout`) |
| Errors | `errs.Register*`, `grpcx.FromError`, `httpx.RespondError` |

In dev the servers serve plaintext h2c. Set `GRPC_TLS_CERT_FILE` /
`GRPC_TLS_KEY_FILE` (and `GRPC_TLS_CLIENT_CA_FILE` for mTLS) to serve TLS, and
give the client `TLS: &grpcx.ClientTLSConfig{...}` instead of `Insecure`. In
prod and stage, `GRPC_REQUIRE_TLS=true` makes `Build` refuse a plaintext
gRPC server.
